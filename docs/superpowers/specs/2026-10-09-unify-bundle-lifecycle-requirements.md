# Unify bundle lifecycle — requirements as explicitly stated by the requester

Companion to [2026-10-09-unify-bundle-lifecycle-design.md](./2026-10-09-unify-bundle-lifecycle-design.md).

**Purpose.** A reviewer-facing checklist of what the requester actually asked for, so the
design can be audited against *their* intent rather than against the designer's inferences.

**Scope rule.** Every item below traces to something the requester said. Nothing here is a
designer inference, an audit recommendation, or a derived design decision. Items the
designer added on their own initiative are deliberately **excluded** — see
[§4](#4-explicitly-excluded-from-this-list) for what that means for review.

**Provenance column:**

- **stated** — raised by the requester unprompted, in their own words.
- **chosen** — selected from options the designer presented. Still an explicit decision, but
  the framing was the designer's, so the option set itself is fair game for review.

---

## 1. Functional requirements

| ID | Requirement | Provenance | Verbatim source |
|---|---|---|---|
| FR-1 | Unify the bundle lifecycle — install, uninstall, update — which today has two distinct implementations, one in the CLI and one specific to the extension. | stated | "currently we have two clear distinct path for the bundle lifecycle (install/uninstall/update) one lives in the cli and the other is specific to the extension" |
| FR-2 | Eliminate the duplicated bugs, duplicated maintenance, and divergent behavior caused by having two paths. | stated | "Because we have those two paths we have bug and maintenance on both and even behavior that are not the same." |
| FR-3 | Fix the named symptom: installing a custom agent at user level in VS Code installs bundles into the hidden VS Code folder, whereas the CLI installs correctly to `~/.copilot/agents`. | stated | "For example installing a custom agent in a vscode at user level is installing bundles in the hidden vscode folder. But with CLI when installing it install properly to ~/.copilot/agents." |
| FR-4 | For users with bundles already installed via the extension, transfer the installed agents / instructions / prompts to user level in one shot. | stated | "For people with bundle already installed via the extension I would like to transfer at user level in one shot the installed agents / instructions / prompts..." |
| FR-5 | Where there is further opportunity to share code beyond the minimum, take it if worthwhile. | stated | "What would remain splitted if I choose A if there is the opportunity to put more in common it might be worth considering it" |
| FR-6 | Unify bundle download as well, with authentication being the only part allowed to differ per delivery layer. | stated | "Regarding the download of the bundle could it be unified with just the authentication that might differ ?" |
| FR-7 | Drop both APM source types. | stated | "I would unify as recommended but drop both apm source types" |
| FR-8 | Explain what the CLI's `local` source covers today versus the extension's local variants (excluding APM). | stated | "also what is local covering today in cli in comparison to the other local from the extensions ? (except the apm one)" |
| FR-9 | Use `~/.copilot/mcp-config.json` as the user-level MCP configuration file, per the cited VS Code documentation. | stated | "For the mcp the new configuration file coming even within vscode is the following for user level ~/.copilot/mcp-config.json you can read for more details <https://code.visualstudio.com/docs/agent-customization/mcp-servers#_configure-the-mcpjson-file>" |
| FR-10 | Support: developer A installs and commits the `.github` folder; developer B works with kiro and does **not** want to commit their changes. | stated | "what if someone install and commit the github folder but then another one works with kiro but do not want to commit the changes. Would it be properly managed ?" |
| FR-11 | Support the same situation where developer B **does** want to commit the kiro files too. | stated | "What if he actually want to commit also for kiro ?" |
| FR-12 | Fix cross-user lockfile replay: the extension generates a `sourceId` per user/computer, so another user installing from the committed lockfile fails because they do not have the same source id. | stated | "currently with the lockfile generated by the vscode extension, the sourceId used for lockfile is generated temporarily per user / computer so if another user try to install from the lockfile it does not work because he do not have the same source-id. Would that be solved with the current changes ?" |
| FR-13 | Enumerate additional scenario combinations beyond those named, and produce a lockfile solution covering all of them. Additional or different files are permitted. | stated | "Do not hesitate to formulate additional combination hypothesis and come up with a lockfile solution that cover all of it. You can also consider using different /additional files." |
| FR-14 | Present at least two distinct lockfile solutions with a recommendation and reasoning. | stated | "Propose me at least 2 different solutions and which one you recommend and why." |
| FR-15 | The lockfile must support a future workflow where one CLI command installs to a specific target, avoiding the need to commit files for all harness types. | stated | "My goal later will be to with one cli command to install to a specific target (to avoid having to commit the files for all harness types)" |
| FR-16 | **AMENDED — see [§5](#5-amendments-after-review).** Repository-level lockfile migration must occur **only** when an update or installation happens — never merely from opening the repository in VS Code — so no dangling change appears in the user's working tree. User-level migration is not subject to this restriction. | stated | "for lockfiles that are at repository level and not at user level the migration should happens only when an update / installation is happening to not create a dangling change for the user just open opening their repository in vscode" |
| FR-17 | Delete the legacy committed lockfile once migrated. | chosen | Selected "Delete it" (qualified by FR-16) |
| FR-18 | Migration must properly account for the fact that most existing lockfiles were created by the VS Code extension, not the CLI, and that the two formats diverge today. | stated | "most lockfile that exist today would be lockfile created by the vscode extension as the cli is not widely used compared to the extension. Is the migration considering this properly ? As there are divergence between the lockfile of the extension and the one from the cli today." |
| FR-19 | Cover all three installation scopes. | chosen | Selected "All three scopes" |
| FR-20 | A shared lockfile is the single source of truth for what is installed at user scope. | chosen | Selected "Shared user lockfile" |
| FR-21 | **AMENDED — see [§5](#5-amendments-after-review).** User-scope installs place real file copies, not symlinks. | chosen | Selected "Real file copies" |
| FR-22 | Workspace scope should behave like the repository installation scope, targeting the main repo of the workspace file. | stated | "actually workspace match more the repository installation scope targeting the main repo of the workspace file" |
| FR-23 | Exactly one repository-style scope exists; the `workspace` label is retired. | chosen | Selected "One scope: repository" |
| FR-24 | The one-shot transfer runs automatically at activation. | chosen | Selected "Automatic at activation" |
| FR-25 | An `apm` source in an existing hub config or lockfile produces a warning and is skipped; the rest of the hub loads normally. | chosen | Selected "Warn and skip" |
| FR-26 | MCP writes go to the portable destinations only. | chosen | Selected "Portable only" |
| FR-27 | No committed per-file checksums; verification is by re-derivation. | chosen | Selected "No — re-derivation is enough" |
| FR-28 | **SUPERSEDED — see [§5](#5-amendments-after-review).** A developer may exclude a committed bundle and may pin a different version locally; local wins. | chosen | Selected "Exclude list + local version pin" |

## 2. Non-functional requirements

| ID | Requirement | Provenance | Verbatim source |
|---|---|---|---|
| NFR-1 | Simplify the architecture as much as possible; do not overengineer the solution. | stated | "I would like to unify while trying simplify as much as possible the architecture to not overengineer a solution." |
| NFR-2 | No big safety nets. | stated | "No need for big safety nets." |
| NFR-3 | Do not complexify the design in response to review feedback. Review-driven additions that contradict NFR-1 / NFR-2 must be identified and rolled back. | stated | "Were some of them contradicting the initial need I had expressed regarding simplicity / overengineering ? I do not want to complexify too much because of the feedback." |
| NFR-4 | Avoid a further breaking change later: whatever is decided now must already accommodate the future lockfile-driven, per-target install workflow. | stated | "If I want the lockfile to allow in the future the installation via the cli based only on the lockfile of the bundle listed does it change anything right now ? I would like to avoid another breaking change later on." |
| NFR-5 | Delivery must be progressive: several PRs, each of reasonable size, each mergeable into `main`. | stated | "I want to make sure that the delivery of this huge refactor can be done progressively in several PR and that each of them should have a reasonable size but be mergeable into the main branch" |
| NFR-6 | Features must be E2E-testable as early as possible in the PR delivery cycle, and larger PRs are acceptable to achieve that. | stated | "I want in the rules for the PR to be able to test as early as possible the different features even if PR are a bit bigger than what you propose. I want to be able to test E2E feature as early as possible in the PR delivery cycle" |
| NFR-7 | The PR-increment constraint belongs in the requirements now, rather than being deferred to a later step. | chosen | Selected "Requirement in §2 now, slicing in the plan" |
| NFR-8 | Verify claims rather than asserting them; corrections must themselves be checked. | stated | "Did you agreed and check all the claims you did correction for ?" |
| NFR-9 | Renaming the lockfile was raised as an opportunity, conditional on whether it helps or complicates migration — not mandated. | stated | "as the product as been renamed ai-primitives-hub it might be also the occasion to rename the lockfile would that also help the migration or complicate it ?" |

## 3. Repository-mandated constraints

Not from this conversation, but binding on any implementation. Included so a reviewer does
not mistake them for designer invention.

| ID | Constraint | Source |
|---|---|---|
| RC-1 | Dependencies point inward only: CLI/Extension → `app` → `infra` → `core`. New domain or use-case logic belongs in `packages/`, not in a delivery layer. | `AGENTS.md`, `packages/AGENTS.md` |
| RC-2 | Strangler-fig migration: extension `src/services/*` become thin delegators to `app`; no new business rules in a service. | ADR-0001, `src/services/AGENTS.md` |
| RC-3 | Dual naming is deliberate: the repo lockfile, the extension `package.json` name/publisher, and `promptregistry.*` command IDs stay as-is. | ADR-0004 |
| RC-4 | Resolve on-disk roots through the injected `AppStorage` port, never `vscode.ExtensionContext.globalStorageUri` directly in new `app` code. | ADR-0005 |
| RC-5 | Start with a focused failing test, implement the minimal change, rerun, then run related coverage. | `AGENTS.md` Working Rules |
| RC-6 | Tests verify observable behavior through public entry points; mock external boundaries, not the unit under test. | `AGENTS.md` Working Rules |
| RC-7 | Update user-facing or contributor documentation with behavior, command, setting, schema, or workflow changes. | `AGENTS.md` Working Rules |
| RC-8 | Add migrations in `src/migrations/`, run them from activation, tag temporary compatibility code `@migration-cleanup(name)`. | `AGENTS.md` Extension Conventions |

Note RC-3 is in direct tension with the design's lockfile rename; the design amends ADR-0004
rather than silently contradicting it. A reviewer should judge whether that amendment is
adequately justified, since NFR-9 shows the rename was raised as a question, not a mandate.

## 4. Explicitly excluded from this list

The following are **designer decisions, not requester requirements**, and a reviewer should
treat them as open to challenge rather than as fixed constraints:

- the `app/deploy` module boundary and the "bundle bytes + scope" seam
- manifest-driven routing on `PrimitiveKind`, and the naming rules per kind shape
- the desired-vs-materialized lockfile split, schema `3.0.0`, and the two-file layout
- `reconcile` and its comparison key, now `(logicalBundleKey, version, sourceId, targetType)`
- the `resolveBundle` / `readBundleFiles` / link-identity port additions
- the `unifiedDeploy` feature flag and the twelve vertical slices
- retiring the MCP tracking sidecar; folding MCP state into materialization records
- idempotent redeploy in place of a staging or rollback contract
- every item in the design's §13 Accepted risks table

Two of these were shaped by requester questions without being requested outright: the
lockfile split answers FR-10/FR-11/FR-13, and the flag answers NFR-5/NFR-6. They should be
reviewed as *proposed means* to those ends, not as the ends themselves.

## 5. Amendments after review

An independent review (2026-10-09) audited the design against this list. Where design and
requirement genuinely disagreed, the question went back to the requester. Their answers below
**change this contract**, so a later reviewer should audit against the amended form. Rationale
for each is in the design's §14.

| ID | Change | Amended requirement |
|---|---|---|
| FR-16 | **Amended** | Repository migration may also be triggered by an **uninstall**. The binding constraint is unchanged: merely *opening* a repository must never migrate or write. Install, update and uninstall are the three permitted triggers; reconcile, the update scheduler and source sync are not |
| FR-21 | **Amended by exception** | Bundle installs at user scope place real file copies. A `local-skills` install keeps its **live directory link**, because the link is the feature rather than the defect FR-3 reported. The exception is named and bounded; no other case links |
| FR-28 | **Superseded** | There is no local desired state — no `excludes` list and no local version pin. The committed lockfile is the only desired state, and a developer who wants to diverge edits it and does not commit the diff. Git is the override mechanism |
| FR-7 | **Extended** | APM authoring support (the validate command and `apm.schema.json`) is retired as well, in an **independent PR** outside the lifecycle delivery sequence |

Four further requirements were **not** changed, but had an open interpretation that is now
fixed: FR-22 (a multi-root workspace resolves to the first listed folder that is a git
repository), FR-26 (portable-only concerns the four `servers`-keyed VS Code entries, not a
claim about all 11 hosts), FR-27 (re-derivation has a local-state tier that always runs and a
full tier that needs a cached manifest), and FR-18 (legacy non-default-profile MCP configs are
reported rather than migrated).

## 6. Suggested review questions

1. Does each FR/NFR have a specific, locatable answer in the design, or only a gesture at one?
2. Does the design satisfy NFR-1 / NFR-2 / NFR-3, or has it accumulated machinery the
   requester explicitly did not want? Audit §13 Accepted risks and §11 for this.
3. FR-12 is a correctness requirement with a known hard limit — the design states that legacy
   extension rows store release-asset URLs rather than repository origin, so some rows are
   unrecoverable. Is that limit acceptable, and is it surfaced to users rather than silently
   degraded?
4. FR-16 forbids repository migration on workspace open. The design enforces this by a
   call-site rule rather than a threaded flag. Is that sufficient given the update scheduler
   can write at startup?
5. FR-4 says "one shot". Does the design's per-record classification still satisfy that, or
   has it become multi-step for the user?
6. NFR-4: would the proposed schema genuinely avoid a second breaking change when FR-15 is
   implemented, or does it merely defer one?
7. NFR-6: is slice 1 genuinely E2E-testable on merge, by someone who did not write it?
8. Are any FRs answered only for one delivery layer when the requirement implies both?
